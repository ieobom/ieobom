## 0. 한눈에

```
ieobom/  (pnpm 모노레포 · TypeScript)
├── apps/mobile        React Native + Expo  ── supabase-js ──┐
├── packages/shared    앱이 같이 쓰는 값 · DB 타입             │
└── supabase/                                                ▼
    ├── migrations     PostgreSQL 표 · RLS · DB 함수 · pg_cron   Supabase (서울)
    └── functions      Edge Functions ── Gemini · 음성 인식 · 음성 통화 · 알림
```

- 앱은 Supabase에만 붙는다. 바깥 서비스(AI·음성 인식·통화·알림)는 서버 함수가 대신 부른다. 열쇠를 앱에 넣지 않기 위해서다.
- AI는 OpenAI와 같은 호출 방식(Gemini의 OpenAI 호환 주소)으로 부르고, 주소·모델·열쇠는 `.env`의 `LLM_BASE_URL` · `LLM_MODEL` · `LLM_API_KEY`로 뺀다. 모델을 바꿀 때 코드를 고치지 않는다.
- 앱·서버 함수·DB 타입이 모두 TypeScript라 같은 타입과 값을 쓴다. 모노레포와 Expo를 고른 가장 큰 이유다.

## 2. 서버 — Supabase

| 분야 | 선택 | 표시 | 이유 |
|---|---|---|---|
| 데이터베이스 | Supabase PostgreSQL (서울 서버) | 확정 | 처리방침에 '한국(서울) 서버'로 적혀 있고, 19 ERD를 그대로 옮긴다. |
| 보는 사람 규칙 | RLS (행 단위 접근 규칙) | 확정 | 앱이 DB에 바로 붙으므로 '메모는 나만, 답은 둘 다 답한 뒤에만'을 DB가 직접 지킨다. |
| 여러 단계 한 번에 | DB 함수 (`rpc`) | 추천 | 답 열기·초대 연결처럼 두 사람 데이터가 같이 바뀌는 일을 '전부 되거나 전부 안 되거나'로 처리한다. |
| 자동 처리 | 트리거 | 추천 | 메모를 지우면 그 메모로 만든 여쭤볼 이야기도 지우기 같은 일. |
| 정해진 시간 작업 | Supabase Cron (pg_cron + pg_net) | 확정 | 질문 보내기, 하루 한 번 알림, 30일 지난 통화 기록 지우기. |
| 서버 함수 | Supabase Edge Functions (Deno · TypeScript) | 확정 | 바깥 서비스 열쇠는 여기에만 둔다. |
| 로그인 | Supabase Auth + 카카오 | 확정 | 로그인 서버를 따로 만들지 않는다. 문자 인증 없음. |
| 사진 저장 | Supabase Storage | 추천 | 근황 사진을 같은 RLS로 두 사람만 보게 막는다. |
| 실시간 갱신 | Supabase Realtime | 추천 | 연결 완료·답 열림·새 근황을 보고 있는 화면에 바로 반영. |
| 표 변경 관리 | Supabase CLI 마이그레이션 | 확정 | `supabase/migrations`에 SQL로 남겨 언제 무엇을 바꿨는지 추적. |
| 규칙 검사 | pgTAP | 추천 | '상대 답이 먼저 보이면 안 됨' 같은 약관 약속을 자동으로 확인. |
| 운영 도구 | Supabase 관리 화면(Studio) | 추천 | 질문 검토·공지·문의 답변·설문 문항. 시범 운영 동안 관리자 웹을 만들지 않는다. |

### 일을 어디에 둘지

| 어디서 | 하는 일 |
|---|---|
| 앱 → DB 바로 (+RLS) | 목록·상세 보기, 메모·근황 저장, 설정 바꾸기 |
| DB 함수 | 답 보내기·열기, 먼저 보내기, 초대 코드 확인·연결, 연결 끊기, 질문 고르기 |
| pg_cron | 질문 보내기, 하루 한 번 알림 시작, 보관 기간 지난 기록 지우기 |
| Edge Functions | 메모 정리·여쭤볼 이야기(AI), 말 → 글, 전화 걸기·울리기, 알림 발송, 탈퇴(카카오 연결 끊기) |

- Edge Functions가 쓰는 관리자 열쇠(service_role)는 RLS를 건너뛴다. 그래서 서버 함수 안에서는 규칙을 코드로 직접 지킨다.
- DB 타입은 `supabase gen types`로 `supabase/functions/_shared/database.types.ts`에 만들고 `packages/shared`가 다시 내보낸다. 서버 함수(Deno)가 `packages/`를 바로 못 읽기 때문이다.

## 5. 앱에서 꼭 지킬 규칙

- **비공개 내용을 미리 열지 않는다.** '답 열림'·'초대 사용 완료'는 서버 응답을 받은 뒤에 표시한다. 화면을 먼저 바꾸는 방식(낙관적 갱신)을 여기에 쓰지 않는다.
- **로그아웃·계정 전환·연결 끊기** 때 캐시·사진 캐시·실시간 구독을 정리한다. 권한은 RLS가 지키고, 캐시 지우기가 권한 검사를 대신하지 않는다.
- **조회 키**에 `사용자 + 가족 연결 + 조건`을 넣는다. 가족을 바꿨을 때 이전 가족 데이터가 잠깐이라도 보이면 안 된다.
- **실제로 연결된 통화**가 끝났을 때만 통화 후 메모를 띄운다. 취소·거절·못 받음은 구분한다.
- **늦게 온 응답은 버린다.** 메모를 고치거나 지운 뒤 도착한 AI 결과가 화면을 되돌리면 안 된다.
- **저장·답 보내기·초대 수락은 자동으로 다시 보내지 않는다.** 보내는 중엔 버튼을 잠그고, 중복 방지는 DB 함수에서 한다.
- **큰 글씨**는 실제 기기 글자 확대 설정에서 줄바꿈·버튼 높이·읽기 순서를 확인한다.
- **`EXPO_PUBLIC_`에는 공개해도 되는 값만.** Supabase 공개 키(anon)만 앱에 넣고 service_role 키는 절대 넣지 않는다.
- 시안의 시연용 시간(6초, 15초 등)을 실제 값으로 옮기지 않는다.

## 8. 개발 순서

1. **실제 기기 검증:** 카카오 로그인·복귀, 통화 걸기·받기·잠금 화면 수신. 여기서 막히면 다른 화면을 만들어도 소용없다.
2. 표·RLS·DB 함수 (19 ERD → `supabase/migrations`) + pgTAP 규칙 검사
3. 공통 UI·화면 이동·supabase-js 연결
4. 질문·근황·기록·통화 화면
5. 서버 함수: 말 → 글, 메모 정리·여쭤볼 이야기, 알림 발송
6. 알림·권한·접근성
7. 테스트·배포

화면별로 어떤 기술이 쓰이는지는 프론트 12차 비교조사 20절에 있다(38차 화면 번호 기준).
